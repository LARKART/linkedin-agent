## Caption

A 600-comment thread asking people to share their actual agent setups says more than another demo video ever could.

The question wasn't "what can agents do." It was "what does your config actually look like." That's a different conversation.

Most multi-agent systems come down to three decisions, whether teams name them that way or not.

First, who's in charge. Orchestrator-worker is the pattern most people land on, because something needs to decide what happens next. Peer-to-peer setups look more interesting in a diagram. They also cost more to run and get harder to debug when two agents disagree.

Second, where state lives. This is the part that quietly breaks systems. Agents without shared memory repeat work, lose context, or contradict each other three steps later. Shared memory isn't optional once you're past a single agent doing a single task.

Third, who picks the tool. Not which tools exist, who decides which one gets used in a given situation. Skip this decision and you end up with an agent that technically has access to ten tools and reliably picks the wrong one.

The pattern comes before the model. Picking GPT-whatever or Claude-whatever doesn't matter much if the orchestration underneath has no clear owner for state or tool routing.

What does your actual setup look like right now? Orchestrator-worker, peer-to-peer, something else?

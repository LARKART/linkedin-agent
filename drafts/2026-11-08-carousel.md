## Caption

A coding agent asked for permission once. The user clicked "don't ask again." That one click is why security researchers are now finding credentials sitting in plain text across public repositories.

Here's the mechanism, based on recent reporting on a Claude Code permission flaw.

When you approve a command and tell the agent not to ask again, that approval gets written to a local settings file in the project. If the command included a secret, like an API key or token, the secret gets written too. Not masked. Not encrypted. Just saved as part of the rule.

Then someone pushes the repo public, settings file included.

The part worth sitting with: this isn't a model intelligence problem. The agent didn't fail to understand what a secret was. It did exactly what it was told, which was stop asking and remember the answer. The flaw is in the permission design, not the reasoning.

And agents being helpful makes it worse. Ask one to commit your changes, a completely reasonable request, and it may commit the very file holding the leaked credential.

I think about this anytime an automation gets a blanket "always allow" setting instead of per-action approval. Convenience and judgment are usually a trade-off, not a package deal. The more autonomy you hand an agent, the more that autonomy needs boundaries that don't depend on the human remembering to check.

A few things worth checking before your next agent session:

What gets written to disk when you approve an action.

Whether your repo's local settings files are in .gitignore.

Whether "don't ask again" is scoped to a single command or quietly became a standing rule.

Agent permissions deserve the same scrutiny teams already give API scopes and IAM roles. Most people just haven't started treating them that way yet.

## Caption

A security firm called Invariant Labs found something worth paying attention to. A malicious MCP server sitting next to a legitimate WhatsApp MCP server could quietly instruct an agent to read someone's message history and send it to an attacker's number. No prompt from the user. No obvious warning in the tool review screen.

The model did nothing wrong. It just did what it was told, by a tool it had permission to trust.

This is the part people keep missing when they talk about AI agent risk. Everyone is focused on jailbreaking the model. But MCP servers don't have isolation boundaries between each other. A response from one server can influence what happens on a completely different server, in the same context window, with no record of where the instruction actually came from.

OWASP has already catalogued this as its own risk category. JFrog found a separate critical vulnerability in mcp-remote that let attackers execute commands on the host machine just by connecting to an untrusted server. Different bug, same pattern: the danger sits in the integration layer, not the model.

If you're building with agents and tool calling, the model is probably the least risky part of your stack right now. The MCP servers you've connected are the part nobody is reviewing.

Makes me wonder how many teams are auditing their tool stack the way they'd audit a new npm dependency, versus just installing whatever MCP server looked useful.

What's the most repetitive part of your workflow right now, and is it running through a tool you'd actually trust with a security review?

## Caption

A team can now generate a pull request in minutes. Checking that pull request still takes the same amount of time it always did.

That gap just got attention. Harvard research on code review and AI-generated code surfaced on Hacker News this week, with a lot of people arguing about where the real bottleneck sits.

The finding lines up with something worth saying plainly: writing code was never the slow part for most teams. Reading it, tracing what it touches, deciding if it is safe to ship, that was always the slow part. AI just made the first half nearly free and left the second half untouched.

So the math changes. If an agent produces a function that calls three APIs and touches a shared database table, someone still has to trace every one of those paths before it merges. That review doesn't get faster because the code got written faster.

A related post going around makes a similar point from a different angle: not every workflow needs an LLM sitting in the middle of it. Some tasks are better served by a plain script or a deterministic rule, precisely because the output is predictable and doesn't need a human to double check reasoning every time.

That's the actual design question. Before automating a workflow, it's worth asking whether the output will be easy to verify, or whether you're just moving the bottleneck from production to review.

A system that ships fast but can't be checked quickly isn't saving anyone time. It's shifting the cost to whoever has to sign off on it.

Where does review slow your team down right now, writing the code or trusting it?

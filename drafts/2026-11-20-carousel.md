## Caption

Two platform vendors shipped agent governance tooling in the same week.

Google added semantic policy controls. Oracle shipped MCP and A2A connection governance. Different companies, same underlying move.

The question is changing. It used to be: can the agent do this. Now it's: what checks run before it's allowed to try.

That shift matters more than it sounds.

Most agent setups right now rely on a human checking the output after the fact. Someone reviews the email before it sends, approves the record before it updates, checks the action before it fires. That works at low volume. It falls apart once an agent is running dozens of actions a day across multiple systems.

The pattern showing up across these new tools is different. Define what's allowed as policy, separate from the code that does the work. Evaluate the intent against that policy before execution, not after.

It's the same idea as role-based access control, just applied to agent behavior instead of user permissions. Nothing exotic. Just a layer that's been missing.

This is where agent projects usually stall. Not the model, not the tool calling. The part where someone has to decide, in advance, what the agent is actually allowed to touch and under what conditions.

If you're building agents into a real workflow, that policy layer is worth designing before you expand what the agent can do.

What's your approval process for agent actions right now? Still manual, or is any of it written down as policy?

**Topic:** Duplicate Tool Calls After Timeouts in AI Agents
**Why now:** Fresh story (under 1 hour old) tackling a concrete, unglamorous agent failure mode that most teams building agents will hit the moment they move past a demo.

## Caption

A timeout does not mean the tool call failed. It means the agent stopped waiting.

That distinction is where a lot of agent builds break once they leave the demo stage.

Here is the common failure mode. An agent calls a tool to charge a card, send an email, or book a slot. The response takes too long. The agent times out, assumes the call failed, and tries again. Except the first call went through. Now the customer is charged twice, or the email went out twice, or the same slot got booked twice.

The agent didn't make a reasoning mistake. It made a state mistake. It had no way to know whether the first attempt succeeded.

Backend engineers solved this problem years ago for payment systems. Every request gets an idempotency key. The receiving system checks if it has already seen that key before acting on it. If it has, it returns the original result instead of doing the work again.

Agents need the same pattern. Not better prompting, not a retry limit, an actual key tied to the action and a record of what state that action is in.

This has to live in the tool layer. You can tell a model to "be careful not to duplicate actions" and it will still duplicate actions, because the model has no memory of what happened on the other side of a dropped connection. The system calling the tool has to track that, not the prompt.

It is an unglamorous fix for an unglamorous problem. But it is usually the difference between an agent that looks good in a demo and one a team is willing to trust with real transactions.
